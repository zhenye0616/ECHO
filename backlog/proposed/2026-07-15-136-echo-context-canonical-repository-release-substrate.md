# Canonical echo-context repository, self-contained CI, and source-artifact authority

## Why this spec exists

Item 135 proved that the local echo-context extraction is source-independent and behaviorally faithful, but it deliberately ended with one migration branch, no remote, no install, and no runtime authority. Its extraction-finality tests also bind several checks to the then-current HEAD and two operator proofs default to Project_echo Git objects, so blindly publishing that directory would produce a repository that cannot safely evolve or validate itself in hosted CI.

This first gate makes echo-context/main the canonical source authority without confusing source publication with installation or live-state authority. It preserves the exact reviewed extraction as an immutable baseline, creates the private canonical repository, gives clean clones a self-contained quality gate, and seals one explicitly non-installable source artifact for item 137. Project_echo remains the installed runtime and state authority throughout this item. The third-repository split executed here is authorized by the 2026-07-15 successor-repository execution decision and item 135's founder-reconciled merge; the G2 topology record defined two organization repositories and kept the context layer inside echo-dev-platform until split triggers fired, so it is cited for its controls-preservation rule, not as the split authority.

This internal-asset work is permitted by the scope guard because unified machine context across Codex, Claude Code, and Cursor is required by the current ECHO development workflow and Team-product delivery. It is not a parallel commercial roadmap or a second product.

The annotated tag ref `refs/tags/v<version>` points at a tag object whose peeled target is the approved source SHA. The tag push is create-only compare-and-swap, never an ordinary push: it uses Git's empty-expect lease form (`git push --force-with-lease=refs/tags/v<version>: origin refs/tags/v<version>`), which atomically requires the ref to not yet exist at write time, and it succeeds only when the porcelain result reports the ref as newly created (`*`); if an identical expected tag appears between the empty-namespace preflight and the push, an ordinary push would report an adopting `up to date` success — here that same-OID pre-existing ref fails the lease and blocks, because the workflow may adopt no ref it did not create, and the run log records the porcelain created-by-this-run proof. The tag annotation message is byte-exact UTF-8 against a single reviewed oracle: the literal template `echo-context source release\nversion: <version>\nsource-sha: <source-sha>\n` — three LF-terminated lines including the mandatory final newline, no CR, no other whitespace variation, with `<version>` the approved version and `<source-sha>` the full 40-hex approved source SHA; tag creation writes exactly these bytes, and every verification compares the read-back annotation bytes against this template rather than any prose paraphrase. Tag verification runs immediately after the push, reading the ref to the tag object to the peeled commit, and fails unless the peeled commit equals the approved source SHA and the annotation bytes equal the template oracle exactly — a lightweight tag pointing directly at a commit fails. Only after tag verification passes is the release created, with `tag_name` and name both `v<version>`, `draft: true`, and `prerelease: true`, referencing the already-existing verified tag; `target_commitish` is never treated as source authority. Draft-creation readback proves `draft: true` and that the pre-existing tag ref still resolves to the same tag object and peeled source SHA — the draft creation neither replaced, retargeted, nor otherwise mutated the tag. All three deterministic asset names belong to that same-run draft. The publish update sends the API's string-valued `make_latest: "false"` while setting `draft: false` and keeping `prerelease: true`; because `make_latest` is a request parameter that release readbacks do not persist, post-publish verification reads back `draft: false` and `prerelease: true` directly and proves not-latest through a supported semantic observable — the repository's latest-release lookup must not resolve to this release. After each successful write the job reads the created object back and fails on any name, target-source, byte, digest, or flag mismatch. Because a post-call log entry cannot survive a runner or process loss during the call itself, every external write is preceded by a write-ahead attempt marker: immediately before the annotated-tag ref push, the draft creation, each asset upload, and the release-publish update, the job appends and flushes to the run log a marker naming the mutation about to be attempted, its target ref/object/asset, and the run/attempt identity — the marker is durably emitted before the external call is issued, so an interrupted run always shows which write was in flight, and a marker with no recorded response is itself an ambiguous-write signal. After any such marker without a response, reconciliation is read-only. After a lost or ambiguous response at any external write — the annotated-tag ref push, draft creation, any asset upload, or the release-publish update — the job makes no further external write of any kind: no retry, no repeat write, and no deletion. An ambiguous tag push may leave a lone tag in the namespace; an ambiguous draft creation may leave the tag plus a draft; later ambiguities may add partial assets — every such partial state blocks identically. It records every attempted write and its last observed state in the run log and stops for founder disposition. There is no automated cleanup: the founder inspects and removes any partial state manually, and a subsequent fresh dispatch re-enters only through the empty-namespace rule. Before declaring success, the job exhaustively re-lists — with complete pagination — every tag ref, every draft or published release, and every release asset, and succeeds only if the namespace contains exactly the expected annotated tag pointing at the approved source SHA, exactly one published prerelease (correct name and tag, `prerelease: true`, not latest), and exactly the three expected assets whose bytes and hashes match the approved tuple, and nothing else; any other state — including foreign state that appeared after the initial empty-namespace check — blocks for founder disposition. The run log is evidence, never attribution authority, and run attempt is execution provenance rather than a new founder-approved content field. Publication is executed by the guarded workflow under founder approval, never by a builder identity directly.

## Risks

- Extraction evidence could be weakened by rebasing it onto evolving HEAD. The frozen-baseline plus ancestry contract is the fallback; existing evidence bytes are never rewritten.
- Hosted CI could appear green only because the founder machine supplies Project_echo or state. AC3 removes implicit paths and proves a clean sibling-free clone.
- Publishing history could expose a secret. Pre/post full-history scans block the private push/release without printing values.
- Native better-sqlite3 behavior can differ across hosted runners. CI pins Node/npm and uses macOS plus Ubuntu; item 137 separately owns the exact Darwin runtime closure.
- Repository controls may not be enforceable on the current hosting tier. The builder stops for a founder decision and does not claim source-release completion.
- A source archive could be mistaken for an installable runtime. Its filename, manifest, tests, README, and release record all state installable:false and authority:false.
- Remote creation, branch settings, tagging, and release publication are irreversible external mutations. Each is founder-gated and bound to readback evidence.
- The first-release workflow is intentionally not reusable for a populated namespace. Item 137 owns the separately reviewed later-release generalization; absence of that propagation blocks its publication rather than widening item 136 again.
