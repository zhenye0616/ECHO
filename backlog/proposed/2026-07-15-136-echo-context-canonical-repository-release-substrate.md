# Canonical echo-context repository, self-contained CI, and source-artifact authority

## Why this spec exists

Item 135 proved that the local echo-context extraction is source-independent and behaviorally faithful, but it deliberately ended with one migration branch, no remote, no install, and no runtime authority. Its extraction-finality tests also bind several checks to the then-current HEAD and two operator proofs default to Project_echo Git objects, so blindly publishing that directory would produce a repository that cannot safely evolve or validate itself in hosted CI.

This first gate makes echo-context/main the canonical source authority without confusing source publication with installation or live-state authority. It preserves the exact reviewed extraction and completed private-repository bootstrap as immutable history, gives clean clones a self-contained quality gate, and seals one explicitly non-installable source artifact for item 137. Project_echo remains the installed runtime and state authority throughout this item. The third-repository split executed here is authorized by the 2026-07-15 successor-repository execution decision and item 135's founder-reconciled merge; the G2 topology record defined two organization repositories and kept the context layer inside echo-dev-platform until split triggers fired, so it is cited for its controls-preservation rule, not as the split authority.

This internal-asset work is permitted by the scope guard because unified machine context across Codex, Claude Code, and Cursor is required by the current ECHO development workflow and Team-product delivery. It is not a parallel commercial roadmap or a second product.

After fresh convergence, a fresh Codex builder repairs that branch without rebasing or rewriting cycle-one history, and a different independent reviewer evaluates the corrected exact Project_echo and echo-context heads. AC4's evidence-carrying landing gate then lands an exact merge commit `M` and verifies the three hosted checks again at `M`. Only a fresh detached clone of authenticated canonical `main=M` may enter either release workflow. No implementation head reviewed in cycle one is merge or release authority.

Release uses two separate manual workflows with one immutable authorization operation between them. `.github/workflows/source-release-build.yml` is the first dispatch and has `contents: read` only. Its explicit inputs are source SHA, version, and expected lock hash; it fails unless `github.ref == refs/heads/main`, `github.sha`, the source input, and authenticated canonical main all equal `M`, the version equals committed `package.json`, the lock hash equals the SHA-256 of the `package-lock.json` blob at `M`, and `github.run_attempt == 1`. It checks out a fresh detached clone, proves extraction-baseline ancestry, and invokes `build:artifact` exactly once. Before upload it writes the seven-field inner tuple—source SHA, source tree, version, source-archive SHA-256, lock hash, manifest hash, and build run ID—then uploads exactly one workflow artifact named `echo-context-<version>-release` containing the three AC5 files plus that tuple record. The raw un-extracted ZIP returned by the exact-artifact-ID API is the workflow artifact; its SHA-256 is the workflow-artifact digest. The completed build run exposes the artifact ID and digest, yielding the nine-field tuple. It has no environment, tag/release API call, publication controller invocation, or write-capable job.

After the build completes, the delegated coordinator downloads that raw ZIP by exact build run ID and artifact ID, verifies the API ownership/name/expiry metadata and ZIP digest before safe extraction, and independently verifies the inner tuple and all three release files without rebuilding. It then creates canonical JSON `source-release-approval.v1.json` under `schemas/source-release-approval.v1.schema.json`, binding: item ID; converged specification commit and fresh `ready_content_sha`; delegation decision; repository ID/node ID/owner/name/private visibility; source SHA/tree/version; source-archive SHA-256; checksum-file SHA-256; lock hash; manifest hash; build run ID/attempt; workflow artifact ID/digest/name; tag, release, and three asset names; `artifact_kind: source`, `installable: false`, `runtime_authority: false`, `state_authority: false`, and `maturity: DEV`; exact publication-plan SHA-256; a unique single-use nonce; and the literal no-retry/no-adoption/no-cleanup ambiguity policy.

The coordinator prepares—but does not yet publish—an authorization commit whose parent is exactly `M`, whose tree contains exactly one mode-100644 file named `source-release-approval.v1.json`, and whose commit message and author/committer identity/timestamp are fixed in the prepared execution plan. It computes the exact authorization commit OID and JSON SHA-256 locally. Before the authorization-ref write, the canonical JSON Project_echo record `raw/internal/migrations/2026-07-15-136-echo-context-source-release-delegated-authorization.json` is committed to public Project_echo `main` and validated by the landed target schema `schemas/project-echo-delegated-operation-authorization.v1.schema.json`; it binds the complete approval tuple, JSON hash, authorization commit OID, exact ref `refs/heads/release-authorizations/<nonce>`, build run/artifact identities, publication-plan hash, and intended operation. Only after authenticated Project_echo origin/main readback proves that exact record does the coordinator make one create-only target write:
`git push --porcelain --force-with-lease=refs/heads/release-authorizations/<nonce>: origin <AUTH_COMMIT>:refs/heads/release-authorizations/<nonce>`.
Only a single `* [new branch]` row for the exact ref succeeds. Authenticated readback must prove the ref OID, commit parent, one-file tree, and JSON bytes/hash. Lost/ambiguous response, a pre-existing ref even at the identical OID, malformed/additional porcelain, or any readback mismatch means read-only reconciliation and no publish dispatch. The authorization ref is immutable audit evidence: never update or delete it, include it in complete-ref secret scans, and never treat it as target-main source.

`.github/workflows/source-release-publish.yml` is a second manual dispatch, has no build step and no environment, and gives its sole `publish-release` job only `contents: write` plus `actions: read`. Committed `tools/verify-source-release-authorization.mjs` owns the pre-write authorization verification. Inputs bind source SHA/version, build run ID, workflow artifact ID/digest, nonce, authorization ref/OID/JSON hash, and the exact Project_echo authorization-record commit/path/hash. Before checkout, download, or mutation it fails unless `github.ref == refs/heads/main`, `github.sha` and authenticated target main equal the approved `M`, `github.run_attempt == 1`, the target repository identities are exact, and the authorization ref readback equals the input OID. It verifies the authorization commit parent and one-file tree, parses the canonical JSON under the committed schema, and matches every field to the dispatch and live repository. It fetches only public Project_echo governance evidence, proves the supplied record commit is an ancestor of authenticated Project_echo `origin/main`, reads the exact path at that commit, verifies its hash/schema, and requires that record to bind the same authorization ref/OID/JSON and full publication tuple. This read introduces no credential or Project_echo write; mutable Project_echo branch bytes are never approval authority.

Both workflows use separate constant concurrency groups with `cancel-in-progress: false`, per-job attempt-one guards, and terminal `always()` rerun sentinels listing every other executable job in `needs`, so any full, failed-job, or single-job rerun fails with no substantive work. The publish workflow's `run-name` contains the nonce. Before any write it fully paginates publish-workflow runs and jobs and fails if any other dispatch with that nonce exists; serialization ensures two concurrent dispatches cannot both pass. A pre-write failure consumes the nonce and authorization ref: recovery requires a fresh build dispatch, new nonce/authorization commit/ref, and new Project_echo authorization. A replaced never-started pending run is proven non-mutating only when run/job readback shows no job and no write, but its nonce/ref are still consumed and never reused. Cancellation or runner loss after start follows the fail-stop contract below.

The publisher downloads the raw ZIP only through the exact build run/artifact IDs, verifies ownership, exact name, unexpired state, and workflow-artifact digest before extraction, safely extracts exactly the tuple record plus three files, verifies all nine tuple fields and approval fields, and runs `verify:artifact` against the approved manifest hash without rebuilding. Immediately before its first release mutation it again proves repository identity, canonical `main=M`, authorization identities, and a fully paginated empty destination release namespace: no tag ref, draft/published release, or release asset. Any foreign or apparently attributable entry, authentication error, malformed response, pagination loop/truncation, or readback ambiguity blocks.

One exported `runPublication(input, deps)` state machine in `tools/release-publication-controller.mjs`, invoked through one production CLI adapter, owns every AC6 tag/REST mutation. HTTP, Git subprocess, filesystem reads, diagnostics, clock, and hard-loss checkpoints are injected so tests execute the production state machine; test adapters never form a second mutation implementation. The fixed write order is annotated-tag create-only push → exact tag readback → draft POST → exact draft readback → archive upload/readback → checksum upload/readback → manifest upload/readback → publish PATCH → exact post-publish readback. The tag write source is the preverified immutable `TAG_OBJECT_OID`, never mutable `refs/tags/v<version>`, and uses exactly `git push --porcelain --force-with-lease=refs/tags/v<version>: origin <TAG_OBJECT_OID>:refs/tags/v<version>`. Each mutation is attempted exactly once with transport retries disabled. The only accepted responses are: porcelain exactly one `* [new tag]` row for the captured immutable tag-object OID; draft HTTP 201 with parseable body carrying the captured numeric release ID and exact tag/name/`draft:true`/`prerelease:true`; each upload HTTP 201 with parseable body carrying a new numeric asset ID and exact release binding/name/size/`state: uploaded`; and publish HTTP 200 with parseable body carrying the same release ID/tag/name and `draft:false`/`prerelease:true`. Any malformed or mismatched success body is ambiguous even if later destination state looks correct. The sanitized tag porcelain proof—flag, destination ref, and captured tag-object OID—is emitted as best-effort evidence.

The controller retains the captured release record and all three `{id, release_id, name, size, sha256, expected_bytes}` asset records. After each unambiguous response it performs exact-ID authenticated metadata and byte readback before the next write. The annotated tag object and byte-exact UTF-8 oracle `echo-context source release\nversion: <version>\nsource-sha: <source-sha>\n` (three LF-terminated lines) remain bound to the approved source; a draft cannot create or retarget it; uploads remain strictly serial; publish sends string `make_latest: "false"` and the latest-release observable must not resolve to this prerelease. Immediately before success, the controller completely paginates and re-reads the namespace again, proves the exact tag-object OID/peeled source/annotation, exact captured release ID/tag/name/flags, and an asset-ID set equal to the three captured IDs, then re-fetches exact metadata and re-downloads/re-hashes every captured asset. Matching names or bytes under a different release/asset ID fail; same-content delete/recreate, ID drift, extra/missing/foreign objects, changed bytes, or changed flags fail.

Destination namespace readback is the sole durable publication authority; run logs and markers are best-effort diagnostics only. Each next write requires both an unambiguously successful response and exact authenticated readback of the prior write. If the controller survives a timeout, lost/ambiguous response, malformed success, or failed/ambiguous readback, it may perform read-only reconciliation only and then exits nonzero with zero retry, repeat write, delete, cleanup, adoption, or later mutation. Under process death, runner loss, or cancellation, the lost controller performs no later mutation and no later/downstream job has write scope; no post-mortem log guarantee exists. Tag-only, tag-plus-draft, partial-assets, and apparently-complete namespaces all block identically. Manual cleanup/disposition may occur only as its own separately authorized external operation; re-entry always uses a new build, nonce, authorization ref, Project_echo record, and publish dispatch after a complete authenticated empty-namespace preflight.

## Risks

- Extraction evidence could be weakened by rebasing it onto evolving HEAD. The frozen-baseline plus ancestry contract is the fallback; existing evidence bytes are never rewritten.
- Hosted CI could appear green only because the founder machine supplies Project_echo or state. AC3 removes implicit paths and proves a clean sibling-free clone.
- Publishing history could expose a secret. Pre/post full-history scans block the private push/release without printing values.
- Native better-sqlite3 behavior can differ across hosted runners. CI pins Node/npm and uses macOS plus Ubuntu; item 137 separately owns the exact Darwin runtime closure.
- The current private personal Free topology cannot stop a malicious or compromised sole owner from bypassing policy. AC4/AC6 make that limitation explicit and instead fail closed on stale identity, unreviewed bytes, missing immutable Project_echo authorization, compare-and-swap drift, duplicate nonce, or ambiguous destination state; paid server enforcement remains a future topology upgrade, not an item-136 claim.
- A source archive could be mistaken for an installable runtime. Its filename, manifest, tests, README, and release record all state installable:false and authority:false.
- Repository creation and baseline publication are already-completed immutable history and may never repeat. Target-main landing, authorization-ref creation, tagging, and release publication each require a single-use delegated authorization bound to exact objects/plan plus authenticated response/readback evidence.
- The first-release workflow is intentionally not reusable for a populated namespace. Item 137 owns the separately reviewed later-release generalization; absence of that propagation blocks its publication rather than widening item 136 again.
