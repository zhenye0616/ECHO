# Capture gate (chokepoint pure function)

## What

The architectural chokepoint that every captured event MUST pass through to be persisted. Pure function — input → output. The gate decides accept/reject by consulting the allowlist (item 003), logs the decision (via item 002), and returns a result. It does NOT write to storage; the caller decides what to do with an accepted event.

Public API:

```ts
// src/capture/gate.ts
import type { CaptureEvent } from '../storage/interface.js';

export interface CandidateEvent {
  // Same fields as CaptureEvent except no `id` (gate is upstream of storage).
  source: string;          // e.g., 'app:com.todesktop...', 'domain:app.slack.com', 'fs:/path', 'api:github'
  timestamp: string;
  content: string;
  metadata?: Record<string, unknown>;
}

export type RejectionReason =
  | 'unknown_app'
  | 'unknown_domain'
  | 'unknown_path'
  | 'unknown_api'
  | 'malformed_event';

export type GateResult =
  | { accepted: true; reason: 'allowlisted' }
  | { accepted: false; reason: RejectionReason };

export function gate(event: unknown): GateResult;
```

Behavior:

- The `event` parameter is `unknown` — the gate is the validation boundary. It never trusts callers.
- Source string convention: `<kind>:<id>` where `kind ∈ {app, domain, fs, api}`. Gate parses the prefix and routes to the appropriate `isAllowed*` predicate from the allowlist.
- Malformed event (missing fields, wrong types, unknown kind prefix, etc.) → `{ accepted: false, reason: 'malformed_event' }`.
- Well-formed event whose source is not in the allowlist → `{ accepted: false, reason: 'unknown_<kind>' }`.
- Well-formed event whose source IS in the allowlist → `{ accepted: true, reason: 'allowlisted' }`.
- Every call emits exactly one log entry via the logger (source: `capture.gate`):
  - Accept → `info` level, payload includes `source`, `timestamp`
  - Reject → `warn` level, payload includes `source` (if extractable), `reason`
- Pure aside from the single log emission: same input → same output, no internal state, no I/O beyond the log write.

## Why

This is the architectural enforcement of [[sandboxed-capture]]: events from non-allowlisted sources cannot enter storage by construction, because they cannot get past the gate. The single chokepoint design is what makes the security claim auditable — there is exactly one function in the codebase that decides what gets in.

Pure-function design has three concrete benefits:
1. **Testing is trivial.** No mocks, no fixtures for storage, no async setup. Construct an event, call the gate, assert the result.
2. **Audit is tight.** Every reject decision lands in the log with its reason code. The audit page can later render rejection counts ("ECHO blocked 47 events from non-allowlisted sources today") as proof the gate is working.
3. **Storage stays decoupled.** Gate doesn't know SQLite from MemoryStorage. The caller (a future "capture pipeline" item) wires an accepted event into whatever storage is configured. Swapping storage doesn't touch gate logic.

The decision to make gate emit logs (rather than be 100% pure) is intentional: one observable effect per call gives us the audit trail, and the log is structured enough that "pure aside from this one effect" is a defensible claim.

  - Pure: gate does not throw on any input; always returns a `GateResult`

## Out of Scope (Don't Drift)

- **Writing accepted events to storage** — the gate returns the result; a later "capture pipeline" item wires accept → storage.append
- **Capture surfaces** (Swift shim, FS watchers, extension bridge, API connectors) — all later, separate items
- **Rate limiting, throttling, deduplication** — defer
- **Encryption of accepted events** — storage layer concern, V1.5+
- **The audit page wire-up** — separate later item
- **Modifying the allowlist file** — gate is read-only against the allowlist; changing the allowlist is a separate code edit + commit
- **Fancy error types or exceptions** — `gate` always returns a `GateResult`; never throws (defensive at the boundary)
- **Embedding generation, content hashing, dedup keys** — V1.5+
- **Anything that reads from or writes to disk beyond the log line** — the gate's purity is part of its contract
