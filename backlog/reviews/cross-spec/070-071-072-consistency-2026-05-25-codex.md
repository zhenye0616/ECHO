# Cross-spec consistency review — 070 / 071 / 072

## Summary

The three specs are directionally coherent: 070 creates the global home, 071 defines role TOMLs, and 072 wires agent adapters. The load-bearing risk is ownership of shared contract surfaces: `AgentProfile`, `types.ts`, `~/.echo/skills`, the default role list, and build-order gating are each claimed or assumed by more than one spec. I would not let 072 be claimed as-is, and I would patch the 070/071 handoff language before builders lock in the current names.

## Findings

### F1 — `AgentProfile` is two incompatible contracts, and `types.ts` has no clear owner
**Specs involved:** 070, 071, 072
**Severity:** block
**The issue:** 070 says `src/echo-home/paths.ts` exports schema types and explicitly exports `AgentProfile` for `onboarding.json` with `id`, `detected_at`, `wired_at`, `probed_at`, `capabilities`, and `wire_error` (`070:53-56`, `070:82-99`, `070:132-141`). 072 separately lists `src/echo-home/types.ts` as a file to extend (`072:18`) and defines another `AgentProfile` for sync inputs with `kind`, adapter `paths`, `echoSection`, and MCP config snapshots (`072:132-150`). Those are not the same shape, despite 072 saying it is "extended from 070's types" (`072:133`). 071 also creates `src/echo-home/index.ts` as a barrel (`071:12-13`, `071:121-124`), which makes a future export collision likely if both names enter the public surface.
**Recommendation:** Rename one contract before implementation. Prefer renaming 072's input DTO to `AdapterSyncProfile` or `SyncAgentProfile`, and remove the "extended from 070's types" language. If the set wants a shared `src/echo-home/types.ts`, make 070 explicitly own that file and move/rename the onboarding record there, e.g. `OnboardingAgentProfile`, then have 072 add sync-specific types non-destructively. Do not leave builders to infer whether `types.ts` exists.

### F2 — No spec actually populates `~/.echo/skills/`
**Specs involved:** 070, 071, 072
**Severity:** block
**The issue:** The parent design makes `~/.echo/skills/` the canonical skill library (`design:34-49`). 070 creates that directory empty and says skills are populated by 071 (`070:64-74`, `070:197-200`). 071 does not populate it: it only ships role TOMLs in `assets/echo-roles/`, says 070 owns `~/.echo/`, and explicitly says not to add skills (`071:59-69`, `071:269-281`). 072 then reads skills from `~/.echo/skills/` and copies them to `~/.claude/commands/` (`072:106-115`, `072:152-155`). Implemented in this order, Claude Code skill sync succeeds mechanically while copying zero files.
**Recommendation:** Assign skill-library population to exactly one spec. The cleanest local fix is to make 072 own the repo-skills-to-`~/.echo/skills/` copy before `syncClaudeSkills`, because 072 already owns adapter sync and skill copying. A simpler alternative is to change 072's source of truth from `~/.echo/skills/` to the in-repo `skills/` directory and change 070's comments so `~/.echo/skills/` is a future cache, not a V1 prerequisite. Either way, remove 070's claim that 071 populates skills unless 071 is actually amended to do so.

### F3 — 072 is implementation-gated but still selectable by `tools/blocked.py`
**Specs involved:** 070, 071, 072
**Severity:** block
**The issue:** 072 frontmatter says `blocked_by: []` (`072:1-9`), but its own body says implementation assumes 070 and 071 have landed and tells a builder to escalate if picked before they are in `complete/` (`072:57`). The parent design also says "071 + 072 are independent and can run parallel" (`design:126`), while 072's role-copy and `syncAll` contracts depend on 071's assets and 070's home paths. With the current frontmatter, the deterministic selector can hand 072 to a builder first, producing avoidable churn.
**Recommendation:** Set 072 `blocked_by` to both `2026-05-25-070-echo-global-home-scaffold` and `2026-05-25-071-role-definition-format-and-defaults`. If preserving parallelism is important, split 072 into an adapter-primitives spec that excludes role sync / `syncAll` defaults, then keep the orchestrator spec blocked on 070 + 071.

### F4 — Default role list ownership is duplicated
**Specs involved:** 071, 072
**Severity:** pushback
**The issue:** 071 owns and tests the three shipped role assets under `assets/echo-roles/` (`071:14-18`, `071:175-236`, `071:257-260`, `071:326-331`). 072 AC5 says the `defaults` list is supplied by 073/074 and "this engine does not hardcode the list" (`072:117-122`), but AC6 immediately gives `syncAll` a default `['strategist.toml', 'reviewer.toml', 'builder.toml']` (`072:130-156`). If 071 adds or renames a default role, 072 silently lags.
**Recommendation:** Make 071 the owner of the default-role filename list, e.g. export `DEFAULT_ROLE_FILENAMES` from `src/echo-home/roles.ts` or a small adjacent module and re-export it through `src/echo-home/index.ts`. Then 072 imports that constant, or else 072 removes its default and requires callers to pass the list. Also remove the "same mechanism 070 uses to find repo-bundled assets" wording in 072 AC6 (`072:156`); 070 defines home paths, not repo asset resolution.

### F5 — Role loader `skillsRoot` handoff is implicit
**Specs involved:** 071, 072
**Severity:** pushback
**The issue:** 071 validates role `skills` by walking upward from the role file to find `<repo>/skills/` (`071:158-172`). It later acknowledges that this fails when roles live in `~/.echo/roles/` and adds an optional `skillsRoot` overload (`071:301-303`, `071:326-330`). 072 copies default roles into `~/.echo/roles/` (`072:117-128`) but never states what future callers should pass as `skillsRoot`. This is especially ambiguous while F2 is unresolved: the intended root could be repo `skills/` or `~/.echo/skills/`.
**Recommendation:** After deciding F2, add one sentence and one test hook in the owning spec: "When loading roles from `ECHO_HOME_PATHS.roles`, pass `skillsRoot: <chosen canonical skill root>`." If 072 remains the first spec that materializes `~/.echo/roles/`, put the handoff note in 072 AC5/AC6 so 073/074 do not rediscover it.

### F6 — Role schema version policy is under-stated relative to state files
**Specs involved:** 070, 071
**Severity:** nit
**The issue:** 070 requires `schema_version: 1` for state files and says consumers must fail loudly on mismatches (`070:78-128`). 071's TOML schema has no version field (`071:75-120`) but later says the role format is "schema versioned via additive-only changes" (`071:336-346`). The no-version choice can be fine, but the current language makes it sound like role TOMLs have an equivalent version contract when they do not.
**Recommendation:** Prefer clarification over adding a field. Amend 071 to say role TOMLs are intentionally unversioned in V1 and governed by strict validation plus explicit follow-up migrations for breaking changes. If the strategist wants parity with 070 instead, add `[role].schema_version = 1` now before any default TOMLs ship; do not defer that decision until user-owned role files exist.

### F7 — Several cross-references point to owners that do not own the referenced surface
**Specs involved:** 070, 071, 072
**Severity:** pushback
**The issue:** 072's `spec_refs` points at `backlog/ready/2026-05-25-071-role-definition-format.md`, but the actual file is `backlog/ready/2026-05-25-071-role-definition-format-and-defaults.md` (`072:31-33`). 072 also says 070 creates "base types.ts" (`072:34`) even though 070 only names `paths.ts` and `scaffold.ts` (`070:11-16`). 070 says skill population is 071's responsibility (`070:43-45`, `070:197-200`), while 071 says it does not touch `~/.echo/` or add skills (`071:269-281`).
**Recommendation:** Patch these references after resolving F1/F2. They are small text edits, but leaving them in place forces the first builder of each item to choose between the specs rather than follow them.

## What's NOT a problem (intentional)

- The role asset path itself agrees: 071 ships defaults at `assets/echo-roles/` and 072 points role-sync at that path (`071:14-16`, `071:175-177`, `072:117-122`). The problem is list/constant ownership, not the path string.
- 071 can run in parallel with 070. It ships in-repo TOMLs and a directory-agnostic loader, and no 071 acceptance criterion needs `~/.echo/` to exist (`071:59-69`, `071:269-273`).
- No current 070-072 first use loads roles from `~/.echo/roles/`; 072 only copies bytes. The `skillsRoot` issue becomes load-bearing for 073/074, which is why it should be handed off explicitly now rather than treated as a 071 blocker.
- Ajv for JSON state files and hand-written TOML validation are acceptable together. TOML has no native JSON Schema equivalent in this stack, and 071's strict parser checks plus tests are a reasonable validation philosophy (`070:53-56`, `071:158-173`, `071:238-267`).
- The conflict-detection postures are coherent by ownership class. `ensureEchoHome()` preserves existing runtime state files at file granularity (`070:144-160`); adapter files use marker/key-level conflict detection because ECHO has prior-write snapshots (`072:61-70`); default roles become user-owned after first copy (`072:117-128`). That distinction should be documented for users later, but it is not internally inconsistent.

## Verdict

Block the set as-written before claiming 072. The core design is sound, but the specs need amendments for shared type names, `types.ts` ownership, `~/.echo/skills/` population, and 072's `blocked_by` field. 070 and 071 are close to claimable independently, but their cross-reference language should be patched first so they do not bake in the wrong owners for skills and public types.
