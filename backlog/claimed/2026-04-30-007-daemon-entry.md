# Daemon entry point + lifecycle

## What

A long-lived Node process that hosts the substrate — eventually capture surfaces, eventually the MCP server. For now it boots, idles, and shuts down cleanly. Capture surfaces (item 009) and SQLite (item 008) hook into this scaffold in their own items.

```ts
// src/daemon/index.ts (entry)
import { startLifecycle } from './lifecycle.js';
await startLifecycle();
// idles until SIGTERM/SIGINT
```

```ts
// src/daemon/lifecycle.ts
export async function startLifecycle(): Promise<void>;
```

Behavior:

- **Boot:** acquire PID lock, initialize logger (`createLogger('daemon.lifecycle')`), instantiate `Storage` (MemoryStorage in 007; 008 swaps in SqliteStorage), log `started` with structured payload.
- **Idle:** the process stays alive on Node's event loop. There's no busy loop; no work to do yet. Future items register handlers (FS watchers, MCP server, etc.) that keep the loop active.
- **Shutdown (SIGTERM / SIGINT):** log `stopping`, release the PID lock, log `stopped`, exit 0.

Shutdown handler must be idempotent (a duplicate signal mid-shutdown should not crash).

## Why

Items 001–005 produced a library — code that does things when called. The daemon is what makes ECHO a *running thing* on the user's machine. Without it, capture surfaces have no host process; FS watchers have no event loop to dispatch into; the MCP server has no place to listen.

This item ships the smallest possible daemon — boot, idle, shutdown — so subsequent items (008 swaps in SQLite, 009 registers FS watchers, future items add MCP server) just plug into a stable lifecycle scaffold. Doing the lifecycle right once means every subsequent item gets shutdown handling, single-instance protection, and structured logging for free.

The PID-lock file is a small but important defense: running two daemons simultaneously would race on storage writes, FS-watcher event handlers, and (later) hotkey registration. Cheap to add now, painful to retrofit.

## Acceptance Criteria

- [ ] `src/daemon/index.ts` is the entry; `src/daemon/lifecycle.ts` exports `startLifecycle()`
- [ ] `package.json` adds a `"daemon"` script that runs the entry (e.g., `tsx src/daemon/index.ts` if tsx is already a dev dep, OR `node --import tsx src/daemon/index.ts`, OR a compiled target — pick whichever pattern the bootstrap established)
- [ ] On boot, daemon logs ONE structured entry: `level: info, source: 'daemon.lifecycle', message: 'started'`, payload includes `pid`, `version` (from package.json), `storage_backend: 'memory'`, `data_dir: '~/Library/Application Support/ECHO/'`
- [ ] PID file at `~/Library/Application Support/ECHO/daemon.pid` written on boot, removed on shutdown
- [ ] Single-instance check: on boot, if PID file exists and contains a live PID (verified via `process.kill(pid, 0)`), exit 1 with stderr message `"ECHO daemon already running at PID <n>; refusing to start"`
- [ ] Stale PID file (PID exists but process dead) is overwritten cleanly
- [ ] SIGTERM and SIGINT both trigger shutdown: log `stopping`, release lock, log `stopped`, `process.exit(0)`
- [ ] Shutdown handler is idempotent (second signal mid-shutdown is a no-op, no crash)
- [ ] Shutdown completes in <1s on a quiescent daemon (no hanging handles, no zombie timers)
- [ ] Tests in `tests/daemon/lifecycle.test.ts` use Vitest's `child_process.spawn` to:
  - Boot the daemon, capture stdout, assert `started` log appears
  - Send SIGTERM, assert `stopping` then `stopped` logs appear
  - Assert exit code 0
  - Boot a second daemon while the first is alive, assert exit code 1 + stderr message
  - Boot daemon, kill it ungracefully (SIGKILL), boot again — should succeed (stale PID handled)
- [ ] `npm run test`, `npm run lint`, `npm run typecheck` all clean

## Out of Scope (Don't Drift)

- **SQLite storage** — item 008. This item uses `MemoryStorage`. The line that instantiates Storage should be small and obvious so 008's swap is one-line clean.
- **Capture pipeline integration** — item 006 ships the function; this item does NOT call it. Capture surfaces (009) wire pipeline + watchers into the daemon.
- **Capture surfaces** — item 009 (FS watcher) and later items
- **HTTP / IPC server** — V1.5+; daemon doesn't expose any external interface yet
- **MCP server** — separate item, depends on storage being real
- **Hotkey registration** — Swift shim item, much later
- **launchd plist installation** — separate "install" item; for V1 the founder runs `npm run daemon` in a terminal
- **Crash recovery / supervised restart** — once we ship the launchd plist, launchd handles this
- **Configuration file** — env vars only. `ECHO_DATA_DIR` may be respected for testing, but no JSON/TOML config
- **Cross-platform support** — macOS-only; data dir is mac-specific
- **Adding new dependencies** — none. Use stdlib + what bootstrap installed. PID handling is `fs` + `process`.
