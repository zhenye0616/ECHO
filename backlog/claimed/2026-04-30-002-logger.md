# Logger module (structured, source-attributed, JSON-per-line)

## What

A structured logger module that is the *only* sanctioned way for ECHO daemon code to emit log output. Future modules (capture gate, storage, integrations) all log through this. Output is JSON-per-line on stdout.

Public API:

```ts
// src/logging/index.ts
export interface LogEntry {
  timestamp: string;        // ISO 8601, UTC
  level: 'debug' | 'info' | 'warn' | 'error';
  source: string;           // e.g., 'capture.gate', 'storage.memory'
  message: string;
  payload?: Record<string, unknown>;
}

export interface Logger {
  debug(message: string, payload?: Record<string, unknown>): void;
  info(message: string, payload?: Record<string, unknown>): void;
  warn(message: string, payload?: Record<string, unknown>): void;
  error(message: string, payload?: Record<string, unknown>): void;
}

export function createLogger(source: string): Logger;
```

Behavior:

- `createLogger('capture.gate')` returns a Logger bound to that source. Every entry it emits has `source: 'capture.gate'`.
- Each method writes one line to stdout: `process.stdout.write(JSON.stringify(entry) + '\n')`.
- Level filtering reads `process.env.ECHO_LOG_LEVEL` once at module load; default `info`. Order: debug < info < warn < error. Entries below threshold are dropped silently.
- Payload object is included as-is (must be JSON-serializable; the contract is "you pass valid JSON values").
- No timestamp injection from caller — logger always stamps with current ISO timestamp.

## Why

The capture gate (item 004) needs to log accept/reject decisions. That audit trail is a trust artifact for users (later renderable by the audit page) and a debugging tool for us. Structured JSON beats unstructured text the moment we want to filter by source or level — and we will, immediately.

Every component in the daemon will use this. Defining the contract once, with strict shape, prevents log-format drift across modules. JSON-per-line is the standard format for `jq` pipelines and any structured-logging consumer.

## Acceptance Criteria

- [ ] `src/logging/index.ts` exports `createLogger`, `Logger`, `LogEntry` per the API above
- [ ] Each log call emits exactly one line on stdout, parseable as a single JSON object
- [ ] Entry shape: `{ timestamp, level, source, message }` always; `payload` only when supplied
- [ ] `timestamp` is ISO 8601 in UTC (e.g., `2026-04-30T14:32:00.123Z`)
- [ ] `ECHO_LOG_LEVEL=warn` suppresses `debug` and `info` entries
- [ ] Default level is `info` when env var unset
- [ ] Tests in `tests/logging/index.test.ts` cover:
  - Each of the four levels emits when at-or-above threshold
  - Each of the four levels is suppressed when below threshold
  - Source attribution: createLogger('foo') → entries have `source: 'foo'`
  - Payload preservation: nested objects, arrays, primitives all roundtrip through JSON
  - Default level when env var absent is `info`
- [ ] No external dependencies (no winston, pino, bunyan — just stdout writes)
- [ ] Test suite passes via `npm run test`
- [ ] `npm run lint` and `npm run typecheck` clean

## Out of Scope (Don't Drift)

- **Log rotation / file output / writable streams** — stdout-only. A process supervisor handles file capture if needed.
- **Remote log shipping** (Datadog, Sentry, Loki, etc.) — V2+
- **Pretty-printed dev-mode output / color codes** — JSON-only, consistency wins
- **Async or buffered logging** — sync stdout writes; we are not high-throughput
- **Log sampling, rate limiting, or deduplication** — defer
- **Trace IDs, request IDs, OpenTelemetry integration** — V2+
- **Custom serializers / circular reference handling** — assume payloads are plain JSON values; document as caller responsibility
- **Adopting an external library** — adding a dep is a separate decision; for now, ~30 lines of bespoke code is fine
