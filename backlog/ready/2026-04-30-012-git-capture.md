# Git capture surface (commits via refs watch)

## What

A new capture surface that watches the user's local git repositories for new commits. Each commit becomes one `CaptureEvent` with content = commit message + unified diff. Independent of the chat extractors; both surfaces feed the same storage.

```ts
// src/capture/surfaces/git-watcher.ts
export async function startGitWatcher(
  repoPaths: string[],
  storage: Storage,
): Promise<{ stop: () => Promise<void> }>;
```

Detection:

1. **Real-time:** for each repo, watch `.git/refs/heads/*` and `.git/HEAD` via chokidar. When any of these changes, the head moved (commit, branch switch, rebase). Run `git log <new_head> ^<last_seen_sha> --reverse --format=...` to enumerate new commits.
2. **Polling fallback:** every 30s, run `git rev-parse HEAD` per repo. If different from `last_seen_sha`, kick off the same enumerate-and-emit logic. Catches any missed FS events.

Content per commit:

```
COMMIT <abbrev_sha>: <subject line>

<body, if any>

--- DIFF ---
<unified diff against parent — git diff <parent>..<sha>>
```

Truncate the diff at a reasonable size (e.g., 100 KB) with a `[truncated]` marker — large refactors shouldn't blow up storage in a single event.

## Why

The user's product call: separate "what was discussed" (chat extractors) from "what actually changed" (git). Git is the canonical record of code change — assistants sometimes claim to have edited files they didn't, or partially edit. Git records reality.

This separation also keeps each capture surface simple: chat extractors don't have to detect / parse / extract diffs. Git capture doesn't have to understand chat. Both produce identically-shaped envelopes; the MCP retrieval tool joins them by timestamp at query time.

A new `git_repos` allowlist category is added (option A from the strategist conversation): explicit, reviewable, scoped per-repo. Initial entry: `~/Desktop/Project_echo/` itself, since that's where the founder is dogfooding. Future repos land in their own per-repo PRs.

## Acceptance Criteria

- [ ] `src/capture/surfaces/git-watcher.ts` exports `startGitWatcher(repoPaths, storage)` returning `{ stop }`
- [ ] Real-time watch via chokidar on `.git/refs/heads/**` and `.git/HEAD` per repo (recursive on the refs/heads directory; chokidar handles file create/modify/delete)
- [ ] Polling fallback: `setInterval` every 30s, `git rev-parse HEAD` per repo, compare to in-memory last-seen-sha, trigger enumerate-and-emit if different
- [ ] **Commit enumeration:** when head moves, run `git log <new_head> ^<last_seen_sha> --reverse --format='%H%x09%P%x09%aI%x09%an%x09%s%x09%b'` to get new commits in chronological order. Use `child_process.execFile` to avoid shell injection. (`%x09` = TAB delimiter.)
- [ ] For each new commit:
  - Run `git show <sha> --no-color --format='' --stat` to get files-changed/additions/deletions
  - Run `git diff <parent>..<sha> --no-color` for the unified diff
  - Truncate diff at 100 KB with `\\n[diff truncated at 100 KB; full diff at <sha>]\\n`
  - Build CandidateEvent and `processCandidate(event, storage)`
  - On success: update `last_seen_sha` for that repo
- [ ] **Initial commit handling:** for repos with no prior storage events (`last_seen_sha = undefined`), capture the most recent N commits (default 50) as backfill on first boot, NOT the entire repo history. Configurable via env `ECHO_GIT_BACKFILL_COMMITS` (default 50).
- [ ] **Rebase handling:** rebases produce new SHAs. We capture them as if they were new commits. The original commits remain in storage; this is intentional (append-only audit trail). Acceptable duplicate of content because SHAs differ.
- [ ] On boot, daemon backfills `last_seen_sha` per repo by querying storage for `source: 'git:<repo>', limit: 1, sort: 'timestamp DESC'`

## Out of Scope (Don't Drift)

- **Working-tree state capture** — uncommitted changes are not captured. V1.5+ if useful. Most useful work crosses a commit boundary anyway.
- **Branch / tag operations standalone** — we capture commits, not "user switched to branch X." Branch state is implicit in commit metadata.
- **Remote operations** — pushes/fetches/pulls are not captured. The local commit is the canonical event.
- **Submodules** — V1.5+
- **GitHub integration** (PR comments, issue references) — separate Wave 4 item via the GitHub API
- **Pre-existing commits beyond the backfill window (default 50)** — older history is intentionally not captured. The user dogfoods forward.
- **Cross-repo dedup** (e.g., a commit cherry-picked across repos) — different SHAs, different `source` strings, treated as distinct events
- **Squash detection** — squashed commits are new commits with new SHAs; we capture them as such
- **Adding repos beyond Project_echo** — per-repo additions are separate items so each gets reviewed
- **Non-git VCS** — Mercurial, Pijul, etc. are out
