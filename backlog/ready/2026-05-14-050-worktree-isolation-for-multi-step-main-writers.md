# Worktree isolation for multi-step main writers

## Why this spec exists

On **2026-05-14 14:02 PDT**, a Claude `merge-and-cleanup` session attempting to merge item 048 had its staged 048 conflict-resolution work *swept into a codex-reviewer commit* (`ec2907f review-r6: codex-ops on 2026-05-14-049-codex-skill-adapter`). The cause was structural, not unlucky timing: a parallel codex reviewer launchd-tick (PID 69375) ran `git add` + `git commit` inside the same shared `.git/index` while Claude had unpushed 048 staging in flight. The codex commit captured both file sets. Recovery required soft-reset, lock cleanup, and abandoning the 048 merge cycle for the day.

The merge-and-cleanup skill DOES use a sentinel-file lock at `.git/echo-merge-in-progress` to prevent this — but `grep -rn echo-merge-in-progress skills/ tools/ .claude/` returns exactly two hits, both inside `merge-and-cleanup.md` itself. **No other binding reads or writes that file.** Codex reviewer launchd, watcher, and codex-ops reviewer all operate on `.git/index` with zero awareness of the convention. The lock is one-sided by construction, and adding read-of-lock checks to every other surface multiplies the very prose-as-protocol surface that the collision proved is unreliable.

ECHO's whole design pitch (per `raw/internal/decisions/2026-05-13-echo-skills-are-the-cross-tool-protocol.md`) is that `skills/<name>.md` is the *vendor-neutral peer protocol* — Claude Code, Codex, Cursor's Claude all run the same canonical prose. That protocol exists at the skill layer. **It does not exist at the substrate (git index / fs / process) layer.** Multiple bindings reach into the same `.git/index` as unrelated processes, with coordination implemented as prose conventions in one binding's skills. The 14:02 PDT collision is the first incident where this gap caused production damage; the journal entry at 14:48 PDT is a second, real-time instance (codex strategist and Claude strategist concurrently editing the SAME mcp-interactions-journal.md file during the brainstorm of THIS spec, triggering "File has been modified since read" errors on the Edit tool — the bug class manifesting on the file documenting the bug class).

Builders already solved this: `skills/process-backlog.md` puts all code work in `~/Desktop/Project_echo--<slug>/` worktrees with a feature branch. Two builders cannot collide because they share no `.git/index`. **The collision-prone roles are the ones that DIDN'T inherit the worktree discipline**: reviewers (one `<reviewer>.md` write + journal append + push), watcher (multi-step: combined.md + inline spec patches + next-round request.md + journal append), and merger (multi-step: merge commit + post-merge cleanup move + commit + push).

This spec generalizes the worktree-isolation discipline from builders to all roles that do **multi-step writes to `main`**, deletes the obsolete `.git/echo-merge-in-progress` sentinel-file lock, and explicitly does not introduce any new substrate-level coordination primitive (no `flock`, no scheduler, no broader lock system) — the architectural invariant being established is "no automation writes to the founder's live repo index," not "a new locking layer."

**Per codex strategist's cross-tool consult on Q1+Q2 (atom IDs `3dde6d66` + `f2ef7f5c`, ECHO-mediated):** scope locked at `{reviewers, watcher, merger}`; out-of-scope roles `{atomic-claim step, standalone interactive journal commits}` carved out for separate followups (different failure profile / behavioral discipline respectively).

## Architectural invariant

**No automated role writes to the founder's live `main` checkout's index or HEAD.** Any role that performs multi-step writes to `main` (a sequence of `git add` / `git commit` operations within one logical task, plus its `push`) executes those operations inside a per-tick throwaway worktree created with `git worktree add --detach $TMPDIR/echo-<role>-<uuid> origin/main`, pushes the resulting commit(s) to `origin/main` from there via the existing rebase-and-retry helper, and removes the worktree at tick end (success or failure).

Single-fast-commit roles (atomic-claim) and human-driven interactive roles (founder ad-hoc journal commits) are out of scope (see §"Out of Scope (Don't Drift)").

## Acceptance Criteria

### AC1 — Reviewer wrappers operate inside ephemeral worktrees

- **Modified file:** `tools/review-queue/_run_reviewer.sh` (the shared wrapper invoked by the **headless** reviewer launchd entrypoints only — `run-codex-reviewer.sh`, `run-codex-ops-reviewer.sh`, and any future headless wrapper. **Not invoked by Cursor reviewer ticks** — `_reviewer_gate.py` rejects IDE-mode reviewers per the existing 043 contract. Cursor's worktree lifecycle lives entirely in `skills/review-queue-cursor.md` prose per AC4 below; AC1 does not change Cursor's invocation path.)
- **Per-tick lifecycle (in this exact order):**
  1. In main repo: `git fetch origin main` (read-only — does NOT check out, does NOT touch live index).
  2. Compute `WT="$TMPDIR/echo-${REVIEWER_NAME}-$(uuidgen)"`. Hard-fail if `$TMPDIR` is unset or empty (don't fall back to `/tmp` silently — surfacing the unset-env case is more useful than silently working in a different location than expected).
  3. `git worktree add --detach "$WT" origin/main`. Hard-fail and exit non-zero on error.
  4. **Route the child reviewer process into `$WT` explicitly** — set ALL THREE handoffs: `cd "$WT"` in the wrapper, `export ECHO_REVIEW_QUEUE_REPO_ROOT="$WT"` so the prompt body's mandatory Step 1 (`cd "${ECHO_REVIEW_QUEUE_REPO_ROOT:-$HOME/Desktop/Project_echo}"`) lands in the worktree, AND invoke the child Codex with `codex exec -C "$WT" --sandbox danger-full-access - < "$PROMPT"`. Without ALL THREE the child escapes back to the live checkout and re-enters the shared-`.git/index` race that 050 is built to eliminate. (Convergent finding from R1 codex F1 + codex-ops F3.)
  5. Existing reviewer-tick work (scan `backlog/reviews/**/r*/request.md`, write `<reviewer>.md`, pre-link validate, etc.) executes here. ALL `git add` / `git commit` / `push-with-retry.sh` invocations from this point run inside `$WT` until cleanup. Journal append (`raw/internal/dogfooding/mcp-interactions-journal.md` + HTML regen) also happens in the worktree as a **sibling commit pushed via the same `push-with-retry.sh` BEFORE the cleanup trap in step 6 fires** — explicit ordering, not "same as today," so the worktree-removal-on-EXIT cannot silently drop a successfully-produced journal record (R3 codex-ops F2). **Same-reviewer overlap guard:** before the `git commit` of `<reviewer>.md`, the prompt re-fetches `origin/main` and checks whether `<reviewer>.md` already exists upstream for this round (a sibling tick fired between this tick's initial fetch and now). If yes, exit 0 as a clean no-op (the response was already produced; this tick was a duplicate from launchd cadence overlap). If no, proceed to commit + push as planned. (R3 codex-ops F1 — same-reviewer launchd overlap. Closes the duplicate-noisy-push window that worktree separation made strictly worse than the live-checkout `os.link` guard.)
  6. **Cleanup is unified across success and failure paths** (`trap` on `ERR` and on `EXIT`): `cd` back to main repo, `git worktree remove --force "$WT"`, then `git worktree prune`. The wrapper propagates the child's exit code. **No push-failure-specific preservation logic.** Any failure mode — child crash, push-retry exhaustion, YAML validation rejection, etc. — discards the worktree and its uncommitted/unpushed work. (R2 codex-ops F4 surfaced that the wrapper cannot reliably distinguish push-failure from other child failures without a machine-readable signal the prompt body doesn't emit; rather than invent that signal, 050 accepts uniform lost-work semantics. R2 codex F2 / codex-ops F2 surfaced that plain `mv` corrupts worktree admin metadata anyway. Push-failure preservation is filed as a 050-followup, gated on whether dogfooding surfaces an actual loss; until then, the existing `push-with-retry.sh` retry budget is the only resilience mechanism.)
- **Pre-flight hygiene (step 0, before step 1) — order matters:**
  1. Run `git worktree prune` first to clean admin entries for worktrees whose dirs are already gone (e.g. cleanly-removed prior ticks).
  2. Enumerate `git worktree list --porcelain` and record the set of registered `worktree` paths. **Any path in that set is skipped, no matter its age.** Registered worktrees include active merger conflict-pauses AND any crashed registered tick survivors; 050 does not distinguish them and does not auto-clean either category. Crashed-registered-worktree cleanup is a 050-followup (separate `tools/echo-worktree-doctor.sh` script proposed there).
  3. For each `$TMPDIR/echo-*` directory NOT in the registered set, `rm -rf` it if `find -mmin +60` says it is stale. Unregistered orphans are the only category this pre-flight GCs.
- **No behavioral change visible from `origin/main`'s perspective:** the same `<reviewer>.md` content lands at the same path with the same commit message shape via the same `push-with-retry.sh` retry semantics. Only the CWD of the writing process changes.
- **AC1 wrapper applies to headless reviewers only** (codex `REVIEWER_NAME=codex`, codex-ops `REVIEWER_NAME=codex-ops`). Cursor reviewer ticks (`mode: ide` per `reviewers.json`) follow the IDENTICAL worktree lifecycle prose-encoded in `skills/review-queue-cursor.md` per AC4, but do NOT invoke `_run_reviewer.sh` — the existing `_reviewer_gate.py` rejects IDE-mode reviewers by design (043 contract). Two implementations of the same lifecycle, one in bash (`_run_reviewer.sh`), one in skill prose (AC4); both must produce byte-equivalent worktree management observable from `origin/main`.

### AC5 — `push-with-retry.sh` is CWD-agnostic AND pushes detached HEAD via explicit `HEAD:main` refspec

- **Modified file:** `tools/review-queue/push-with-retry.sh`.
- The script today is invoked from the live main checkout. After AC5 it works identically when invoked from inside a detached-HEAD worktree (`$WT` per AC1/AC2/AC3) or from the main checkout. Internal implementation MUST use `git rev-parse --show-toplevel` (or `--git-common-dir` if the script needs to reach into the main repo's `.git/`) to disambiguate; MUST NOT hardcode `~/Desktop/Project_echo`.

The caller (AC1 cleanup trap) discards the worktree on any failure — no push-failure-specific preservation is wired in 050.

## Out of Scope (Don't Drift)

- **Atomic-claim step in `process-backlog`** — the single-commit `os.link no-overwrite + push` operation that moves an item `ready/X.md → claimed/X.md`. Different failure profile (push-race is already protected; no multi-step staging exposure). Filing as `050-followups.md` candidate, not as 050 work.
- **Standalone interactive journal commits** from human-driven Claude Code / Cursor IDE sessions (e.g. the founder appending a one-line note to `mcp-interactions-journal.md` between TDDs). Mostly behavioral discipline rather than procedural; needs a separate "interactive sessions also use a worktree wrapper OR avoid touching live main mid-other-work" rule.
- **No `flock`, no scheduler, no new substrate lock primitive.** The spec explicitly does NOT introduce any new file-based or kernel-based lock. The architectural answer is "remove the race surface (multi-writer shared `.git/index`)," not "add a coordination layer over the race surface."
- **No defense-in-depth retention of `.git/echo-merge-in-progress`.** It is deleted, not relegated. Keeping it would preserve the one-sided-convention failure mode for whichever future binding next ignores it.
- **No migration of builder worktrees** to `$TMPDIR`. Builders deliberately live at `~/Desktop/Project_echo--<slug>/` for founder inspection during multi-day work. The 050 path location (`$TMPDIR/echo-<role>-<uuid>`) reflects ephemeral-per-tick lifetime and machine-only inspection; the two location choices are intentionally different and BOTH correct for their respective roles.
- **No launchd plist changes.** Reviewer plists (`run-codex-reviewer.sh`, `run-codex-ops-reviewer.sh`) still invoke the same wrapper entrypoints. Only the wrapper's *body* changes (it now creates a worktree internally before doing the existing work).
- **No reviewer-side prose changes for the work itself** (what to read, what to write, where to log). Reviewers see the same `r<N>/request.md` → `<reviewer>.md` contract. They just happen to be in a different CWD.
- **No retro-conversion of past collision artifacts.** The local-only commit `ec2907f` and its backup branch `backup/codex-ops-r6-bad-local-merge` stay as historical artifacts. 050 prevents *future* collisions, does not rewrite past ones.
- **No push-failure preservation.** 050 explicitly does NOT preserve a worktree on push-retry exhaustion. Codex-ops R1 F1 surfaced the breadcrumb-loss concern; R2 codex F2 / codex-ops F2 surfaced that plain `mv` corrupts worktree admin metadata; R2 codex-ops F4 surfaced that distinguishing push-failure from other child failures requires a machine-readable signal the prompt body doesn't emit. Rather than build all three layers of complexity inside this spec, 050 accepts uniform lost-work-on-failure semantics (matches today's reviewer-queue behavior) and files preservation as **050-followup-D**, gated on whether dogfooding ever surfaces an actual production loss.
- **No queue-terminality race fix.** Codex-ops R2 F1 surfaced that worktree separation removes the local-file race guard between reviewer and watcher: a reviewer can be writing `<reviewer>.md` while a watcher in another worktree writes `combined.md` from a stale `origin/main`, OR a reviewer can rebase its response onto a terminal round. This race exists today between any two long-running ticks in the same checkout (different `git index` snapshot times), is not introduced by 050, and an origin-aware terminal check is a separate concern. File as **050-followup-E** — "reviewer/watcher push must re-fetch origin/main and abort-on-terminal" — to be addressed AFTER 050 ships and the race becomes observable in dogfooding.
- **No automatic cleanup of crashed registered worktrees.** Per AC1 pre-flight, registered worktrees are never GC'd. A crashed tick whose ERR trap was also killed (SIGKILL or kernel panic) leaves a registered survivor that accumulates indefinitely. File as **050-followup-F** — `tools/echo-worktree-doctor.sh` operator script to enumerate registered worktrees, identify those with no live process holding them, and offer manual removal. 050 ships without this; manual cleanup via `git worktree remove --force <path>` is the workaround until the followup lands.

## Crash semantics

- **Any tick failure loses unpushed work.** A reviewer / watcher / merger tick that fails for any reason — child crash, push-retry exhaustion, YAML validation rejection, kernel panic — has its worktree discarded by the unified cleanup trap (AC1 step 6) and its unpushed commit lost. This is uniform across all failure modes. Push-failure preservation was proposed in R1 disposition but R2 codex F2 / codex-ops F2 / codex-ops F4 jointly demonstrated it is unimplementable cleanly inside the wrapper boundary; deferred to 050-followup-D (see §Out of Scope). The existing `push-with-retry.sh` retry budget remains the only resilience mechanism for transient push failures; if it exhausts, the tick re-fires on its next cadence with fresh context.
- **Crashed-tick safety is guaranteed by re-fireability, not by recovery.** Ticks are designed to be re-fireable from scratch (this is already a property of today's reviewer-queue loop — see `skills/review-queue-codex.md`'s "One review per tick. **Do not chain reasoning across ticks.**" instruction). The next tick after a crash sees the same `r<N>/request.md` (because nothing pushed) and writes its `<reviewer>.md` fresh.
- **Pre-flight is conservative.** AC1 pre-flight ONLY removes unregistered `$TMPDIR/echo-*` orphans older than 60 minutes. Registered worktrees — including active founder-paused mergers AND crashed registered survivors — are skipped no matter their age. This avoids the founder-data-loss failure mode (codex-ops R1 F2) while accepting indefinite accumulation of crashed registered worktrees as a known issue (cleanup is manual `git worktree remove --force <path>`, or wait for 050-followup-F operator script).
- **Merger conflict-pause across crashes is unchanged.** If a merger tick pauses for founder conflict-resolution and the Claude session crashes during the pause, the worktree is still alive (founder is presumably looking at conflicts in their editor). It is a registered worktree, so pre-flight never GCs it. The recovery story is the same as today: founder either continues the pause manually in the worktree OR aborts and restarts. AC6.4 is the executable test that the new pre-flight does not introduce a worse failure mode here than today's live-checkout merge-and-cleanup.

## Risks / Open Questions

- **Risk R1 — `$TMPDIR` in launchd context.** macOS launchd inherits a per-job `$TMPDIR` that differs from the user's interactive shell `$TMPDIR`. The codex-reviewer launchd plist (per 041) must ensure `$TMPDIR` is set in the job's environment. **Mitigation:** AC1 step 2's hard-fail-with-recognizable-diagnostic surfaces unset-`$TMPDIR` immediately rather than silently writing to `/tmp`; operators verify on first launchd-fired tick after install by running the wrapper once manually (no automatic smoke gate test in 050 — R1 codex-ops F4 proposed one, but the R2 simplification pass de-scoped it: hard-fail message + operator-runbook entry is sufficient discipline given the rarity of plist edits, and adding a mechanical smoke gate would require simulating the launchd environment in CI, which is its own complexity vector). Operator runbook entry to be added in the AC1 commit message of the implementation builder.
- **Risk R2 — Worktree creation cost.** `git worktree add --detach` is ~50-200ms on a warm filesystem with a fully-cloned repo. Reviewer ticks run every 10 min; the overhead is negligible. Watcher and merger ticks fire less often; overhead irrelevant. No mitigation required; noted for completeness.
- **Risk R3 — `push-with-retry.sh` worktree-mode regression.** Today's script presumably works because of a fixed CWD assumption. AC5's test asserts CWD-agnostic behavior, but a subtle path-bug (e.g. the retry's rebase resolving from the wrong tree's HEAD) could pass narrow tests and fail in production. Mitigation: AC6.1 + AC6.2 are end-to-end collision-simulation tests that exercise the full wrapper → worktree → push-with-retry → cleanup path; if any step has a CWD bug, the integration test catches it.
- **Open question Q1 — Should we delete the `backup/codex-ops-r6-bad-local-merge` branch as part of this spec, since it's a historical artifact of the 2026-05-14 collision?** No. Keeping it for a few weeks as forensic evidence is cheaper than wishing we had it back. A separate end-of-month cleanup pass can prune it.
