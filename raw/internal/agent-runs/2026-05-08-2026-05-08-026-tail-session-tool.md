## What I implemented (this attempt)

A fourth ECHO MCP tool — `tail_session` — and the cursor-helper extraction it depends on.

### `tail_session({source XOR source_app, count?, cursor?}) → {turns, next_cursor, source_resolved, warnings}`

The cheap exact-fetch primitive missing from V1's tool roster. `search_memories` is substring + ranking, `get_recent_work_context` is clustered + cross-source. Neither matches the killer-demo case "give me the last N turns from Codex's most-recently-active session," which is why dogfooding 2026-05-08 saw the strategist bypass ECHO twice (13:27 PDT, 14:00 PDT entries in `mcp-interactions-journal.md`) and reach for direct file `grep` instead.

`tail_session` is single-source, recency-only, no clustering, no ranking. Two input modes:

- **Exact `source`:** literal storage `source` field (e.g., `fs:/Users/.../rollout-XYZ.jsonl`). Storage runs the SQL `source = @source` clause (already supported via `QueryFilter.source` at `src/storage/sqlite.ts:97-99`).
- **`source_app` (enum: `cursor | claude_code | codex | git`):** two-step resolution — (1) `source_prefix` query for the newest row under that app's mapped FS prefix, (2) tail that resolved source via the exact-source path. The resolved source is echoed back as `source_resolved` so the consumer can pin subsequent calls.

Cost discipline (all per item 026 acceptance):

- `count` defaults to **5**, clamps silently upward to **20** in the handler. Schema rejects `count <= 0` (`z.number().int().min(1)`); the upper bound is a clamp, not a schema reject. The intentional asymmetry is documented inline in `tail-session.ts:60-66`.
- Composite cursor is `{timestamp, id}` — same shape as `search_memories.next_cursor`, so a cursor from one is decodable by the other (one `cross-tool` regression test in the suite proves this explicitly).
- Source-not-found returns `{turns: [], next_cursor: null, source_resolved: <input>, warnings: ['no captured atoms for this source']}` — NOT an error.
- `source_app` empty store returns `{turns: [], next_cursor: null, source_resolved: null, warnings: ['no captured sessions found for source_app=<app>']}`.
- XOR refinement on (source, source_app): passing both / neither is rejected at the handler entry with an `isError` envelope and structured message. The SDK's `inputSchema` field declares each individually (the SDK's per-field validator can't express cross-field XOR), then the handler runs a Zod `.refine()` and returns `isError: true` if it fails — surfaced cleanly to the consumer rather than thrown as a JSON-RPC validation error.
- Malformed cursor → `isError: true` with no `structuredContent` (matches `search_memories`' contract from item 025 Bug 4).
- `annotations.readOnlyHint: true` — tool only reads from storage.

### Cursor-helper-location decision (per spec's helper-location contract)

**Path taken:** extracted to `src/mcp/tools/_cursor.ts`. The new file is the canonical home; `search-memories.ts` re-exports the same names so any prior caller (tests, future tools) that imports `decodeCursor` from `search-memories.ts` keeps working without churn. `tail-session.ts` imports directly from `_cursor.ts` (the new canonical path). The composite-cursor format itself is unchanged — same base64-of-`{timestamp,id}`-JSON shape — so search_memories' `next_cursor` is still wire-compatible. One regression test (`cursor reuse across tools`) explicitly constructs a cursor via the shared `encodeCursor` and proves it pages tail_session correctly.

Also extracted `searchMatchSchema` from `search-memories.ts` as the single zod source-of-truth for matched-atom shape; `tail-session.ts` reuses it for its `turns: z.array(searchMatchSchema)`.

### Storage-filter exact-match verification

The spec called out: "use `QueryFilter.source` (exact match) — already exists at `src/storage/interface.ts:13` and `src/storage/sqlite.ts:91-95`. DO NOT use `source_prefix` for the exact-source path." Verified by reading both files: `QueryFilter.source` is documented and wired; `sqlite.ts:97-99` adds the `source = @source` clause; the mutual-exclusion check at `sqlite.ts:87-89` would throw if a future caller passed both `source` and `source_prefix`. `MemoryStorage` mirrors this. **No storage change was needed.**

### Schema-vs-runtime exact-or-app branch placement

The spec required schema-level rejection of `(both source AND source_app)` and `(neither)`. The MCP SDK's `registerTool` `inputSchema` field accepts a `ZodRawShape` (object shape literal), not a wrapped schema, so I cannot embed the `.refine()` directly there. Path taken: declare each field independently in `inputSchema` (so the SDK's `tools/list` advertisement keeps the per-field shape consumers expect), then run the wrapped `.refine()` schema inside the handler before any storage work. Failures surface as `isError: true` with the structured message — clean for consumers, not thrown as a JSON-RPC validation error. This matches the SDK's documented pattern for cross-field invariants.
