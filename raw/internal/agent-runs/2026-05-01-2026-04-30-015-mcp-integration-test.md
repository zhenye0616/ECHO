## Decisions made (spec did not pre-specify)

1. **MCP config file paths.** I documented `~/.cursor/mcp.json` for Cursor and `claude mcp add --transport http` for Claude Code. Both reflect the configuration shapes those clients use as of April 2026 to my knowledge. Founder should sanity-check these during manual verification — client config locations have moved between releases. Documented in the troubleshooting section.

2. **Robust grep on the `tools/call` response.** First implementation grepped for `"matches"`. That failed against the live daemon because the MCP SDK wraps the tool's JSON result inside `content[0].text` as a stringified JSON, so the wire bytes contain `\"matches\"` not `"matches"`. Switched the grep to a single ERE alternation that matches either form. Future-proof against an SDK choosing to inline the JSON object.

3. **Smoke-script approach: verify daemon, do not spawn it.** The acceptance criterion phrasing was ambiguous ("Smoke-test script ... that runs the daemon, sends ..."). I interpreted "runs" as "drives [the daemon]," not "starts [the daemon]." Implementation: if the daemon isn't reachable, the script fails fast with a clear "is the daemon running? Start it with: npm run daemon" message. Founder can decide if they want a "smoke + spawn" mode in a follow-up; I noted it.

4. **`Accept` header.** The MCP HTTP transport responds with SSE-format chunks (`event: message\ndata: {...JSON...}\n\n`) when SSE is in the `Accept` list. The smoke script extracts the first `data:` line and falls back to the raw body — robust to either negotiation.
