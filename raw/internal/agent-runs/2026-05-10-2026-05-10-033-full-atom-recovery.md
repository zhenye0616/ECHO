### Decisions made during implementation (not pre-specified)

- **`getAtomAtomSchema.content` is `z.string()` (required), not optional.** Matches AC1's success-shape spec: a successful response always carries verbatim content; the only way to skip content is to land in one of the two error shapes.
- **The `metadata` field on the returned atom is OMITTED (not `metadata: undefined`) when the source CaptureEvent had no metadata.** Mirrors `projectMatch`'s behavior — `m.metadata` is set conditionally — and matches AC1's example output, which shows `metadata: { ... }` on the success shape but doesn't mandate the field's presence on every response. The eighth unit test ("atom with no metadata") asserts `atom.metadata` is `undefined`; the empty-truncations assertion in that test confirms the trust signal still works on metadata-free atoms.
- **`atom_size_bytes` on the error path equals `JSON.stringify(atom).length` of the would-be atom (before envelope wrapping)** — matches AC1's "actual size, e.g. 87_345" diagnostic shape. On `atom_not_found`, it's `0` per the AC1 example.
- **Sister test `tests/mcp/tools/recent-work-context.test.ts` is updated as part of this item.** The test's `expect(names).toEqual([...])` hardcodes the full registered tool set; adding `get_atom` to the server registration without updating this assertion would break the build, defeating AC5's tool-count bump. Updating it is a direct consequence of the spec's mandate to register the tool, not file-list expansion. Logged here for reviewer visibility.
- **Smoke round-trip uses the live store via `search_memories`** rather than synthesizing a test atom. The smoke test runs against a live HTTP MCP daemon; there is no MCP write surface, so "insert a test atom" can only mean "use one already in storage." The unit test layer covers the byte-for-byte verbatim assertion (which can't be done against an unknown source); the smoke sentinel asserts shape + the load-bearing `"content"`-not-in-`truncations` invariant. Skips benignly if the store is empty.
