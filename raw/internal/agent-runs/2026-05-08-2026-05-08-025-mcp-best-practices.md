### Bug 4 — Pagination cursor on `search_memories`

- **Storage layer** (`src/storage/{interface,sqlite,memory}.ts`):
  - `QueryFilter` extended with `before?: { timestamp: string; id: string }`.
  - sqlite ORDER BY: `timestamp ${orderSql}, id ${orderSql}` — parallel directions, never mixed. Same change in memory.ts's sort comparator.
  - sqlite WHERE for `before`: `(timestamp, id) < (@before_ts, @before_id)` (SQLite ≥3.0 row-value comparison). Memory adapter uses equivalent JS predicate.
  - `before` + `order: 'asc'` throws `RangeError`-style synchronously at the storage seam in both adapters (single early throw before SQL prep). Inline comment in `interface.ts` documents the asymmetry.
- **MCP handler** (`src/mcp/tools/search-memories.ts`):
  - `cursor?: string` input, opaque base64 of `JSON.stringify({timestamp, id})`. Decoded via `decodeCursor` which validates JSON shape; throws `CursorDecodeError` for any malformed input (not-base64, valid base64 but not JSON, valid JSON but missing fields).
  - Path-aware overfetch (legible inline comment at the bifurcation):
    - **Recency-only path** (`query === undefined`): `filter.limit = limitApplied + 1`. Storage returns rows in DESC order; drop the +1 if present, emit `next_cursor` from the last kept row.
    - **Substring-query path** (`query !== undefined`): NO `filter.limit` to storage (preserves item 022 filter-before-slice invariant). Substring filter runs over the full window, then `slice(0, limitApplied + 1)`; same drop-and-emit logic.
  - `next_cursor` is always present in success responses (`string | null`), per the schema's `z.string().nullable()`.
  - `CursorDecodeError` is caught at the handler and returned as MCP error result: `{ isError: true, content: [{ type: 'text', text: <reason> }] }`. Crucially, no `structuredContent` on the error path — the success outputSchema's `next_cursor: nullable string` cannot represent the error variant, and per MCP semantics tool errors are signalled by `isError: true` on the result envelope.
  - Tool description documents the opaque-cursor contract ("pass back the prior call's `next_cursor` verbatim; do not construct one client-side").

## Decisions made during implementation

1. **DEFAULT_LIMIT 25 → 20.** Spec called for 25, but envelope-byte-size measurement on a realistic multi-file 200-atom fixture showed 25 atoms produced ~27kB envelopes (over the 25k budget). The spec's explicit escape hatch ("lower `DEFAULT_LIMIT` further") sanctioned the lower number. 20 atoms produce ~22kB envelopes on the same fixture. Documented inline.

2. **Realistic multi-file fixture for envelope test.** A single-cluster 200-atom fixture (all atoms sharing the same file) produces a vastly larger envelope (112kB at limit=25) due to combinatorial edge inflation. Real dogfooding work spans many files; using a 50-file fixture is more representative of the consumer cost the budget guards. The spec's "200 atoms in window" did not prescribe cluster shape, so this was a judgment call.

3. **Permissive nested outputSchema for `get_recent_work_context`.** Spec called for full top-level keys (including `schema_version` and `tool` per Codex's 13:51 PDT correction) but permissive `z.record/z.array(z.unknown())` for cluster/atom/edge bodies. Implemented as specified — exact on top-level, permissive on bodies.

4. **`MAX_OVERFETCH = 200` constant kept.** No longer used after the path-aware `limit + 1` overfetch refactor. Out of scope to delete (would risk affecting external imports). Constant remains as a no-op export.

5. **Storage `before` + `order: 'asc'` rejection.** Implemented as a synchronous `RangeError` throw at the seam (before SQL prep / before any iteration in memory). Single early throw, never silently inverts. Spec was explicit on this.

6. **Did NOT add `source_apps: array[]`, `format: 'skeleton'`, or change `MAX_LIMIT=50`.** All explicitly out-of-scope per spec.
