## What I implemented

A minimal long-lived daemon scaffold:

- `src/daemon/lifecycle.ts` — exports `startLifecycle()`. Resolves `dataDir` from `ECHO_DATA_DIR` (default `~/Library/Application Support/ECHO`), acquires a PID lock at `<dataDir>/daemon.pid`, instantiates `MemoryStorage`, emits a structured `started` log line with `{pid, version, storage_backend: 'memory', data_dir}` (version read from package.json at runtime), keeps the event loop alive via a long-interval no-op timer, and registers SIGTERM/SIGINT handlers. Shutdown is idempotent: log `stopping` (with signal payload), release lock, clear keep-alive interval, log `stopped` — the loop drains naturally and the process exits 0.
- `src/daemon/index.ts` — three lines: `await startLifecycle()`.
- `package.json` — adds `"daemon": "vite-node src/daemon/index.ts"`. `vite-node` is already a transitive dep of `vitest`, so no new dependency was introduced.
- `tests/daemon/lifecycle.test.ts` — spawns the daemon via the `node_modules/.bin/vite-node` binary, streams stdout/stderr line-by-line, parses JSON log lines, and exercises four scenarios.

## Decisions made

- **Choice of TS runner: `vite-node`, not `tsx`/`ts-node`/`--experimental-strip-types`.** Spec offered three options ("tsx if it's a dev dep, OR `node --import tsx`, OR a compiled target — pick whichever pattern the bootstrap established"). None of those was directly viable: `tsx` is not in deps; `node --experimental-strip-types` does not rewrite `.js` import paths to `.ts` resolutions, which is the convention this repo uses (verified empirically); a compiled-target setup would require touching `tsconfig.json` (not in `files_to_modify`). `vite-node` is already in `node_modules` (transitive vitest dep) and resolves `.js`-ext imports to `.ts` files identically to how vitest itself runs the test suite. This keeps the runtime story consistent with the test story and adds zero deps.
- **Event-loop kept alive with `setInterval(() => {}, 0x7fffffff)`.** Without it, `startLifecycle()` resolves and the script hits end-of-file; signal handlers in Node do not by themselves keep the loop alive. The interval is cleared during shutdown so the process exits naturally rather than via `process.exit(0)`. Cleaner: stdout flushes are guaranteed because the loop continues until I/O completes.
- **Single-instance check uses `process.kill(pid, 0)` with try/catch.** ESRCH (no such process) and EPERM (process exists but inaccessible) both throw; both are treated as "not our concern." For our case (same user, same machine) this is correct.
- **Shutdown does NOT call `process.exit(0)`.** Letting the loop drain prevents the trailing-stdout-flush race where `process.exit` truncates buffered output to a piped consumer (which is exactly what tests do).
- **Test fixture spawns the actual `node_modules/.bin/vite-node` binary**, not `npm run daemon`. This isolates the test from npm signal-forwarding quirks and makes the spawn arguments explicit. Each test gets a fresh `mkdtempSync(...)` data dir so tests don't share state.
- **No new dependencies added** (per spec drift rule).
