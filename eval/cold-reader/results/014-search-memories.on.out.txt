1. **What was decided?**  
ECHO would ship `search_memories` as the first real MCP retrieval tool: a read-only raw-event search over captured memories, with optional `query`, `source_prefix`, `since`, `until`, and `limit`, returning matched captured events plus `query_echo`/count metadata. The implementation added `source_prefix` to storage filters, registered the tool on the MCP server, and tested both unit behavior and real MCP server calls.  
Cites: `search_memories` atom `4097ca04-f6fd-421c-a938-b27e74925daa`; `get_atom` atom `f80e642f-0bac-426f-b328-2be07477a194`; `find_clusters` cluster `ctx_da2c4007`.

2. **Why / core reasoning?**  
It was the V1 “killer-demo” bridge: captured Cursor/Claude/git work needed to be retrievable by AI clients through MCP. The chosen shape was intentionally simple: raw substring + source/time filters first, not semantic search or clustering. Later ECHO notes describe this as “raw substring + source-prefix + time-range search” closing the V1 loop.  
Cites: `search_memories` atoms `e9321eba-d5dd-4cc4-b0cc-85ad98fa7565`, `35a81f51-a37a-49f8-9c98-8eebacc30515`, `d9bf0099-11e4-4f6b-ab21-33350a919322`; `get_atoms` atom `4097ca04-f6fd-421c-a938-b27e74925daa`.

3. **Did any reviewer push back?**  
Yes, but not on the core design. The reviewer verdict was **“merge with founder fixups.”** They accepted `source_prefix` and in-tool DESC sorting for V1, but pushed on correctness/perf details: SQLite `LIKE` needed `%/_/\` escaping, `MemoryStorage` limit semantics needed documenting or fixing, and storage-side limit/order/content filtering should be follow-up work. A later efficiency review called the unbounded fetch “fine for V1” but tracked it as future scale work.
